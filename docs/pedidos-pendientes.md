# Envíos pendientes del catálogo público (25 de octubre de 2026)

## Incidente y causa

Un pedido PDF quedó guardado en `sessionStorage` como intento de resultado incierto. Al día siguiente el cliente eligió otra fecha y ventana. El resumen mostraba la selección nueva, pero el botón Confirmar sustituía silenciosamente la solicitud por la guardada bajo `qvd_pdf_pedido_pendiente_${slug}_${cliente.id}`. El servidor rechazó el horario anterior. El problema también alcanzaba pedidos sin PDF: todos usaban el mismo bloque de confirmación. Se reprodujo con API, Vite y SQLite locales: resumen `2026-10-26`, cuerpo POST `2026-10-24`, respuesta `horario_no_disponible`.

## Contrato y recuperación

El resumen de un pedido nuevo es una copia separada del carrito. Antes de abrirlo y otra vez antes de enviar, el navegador consulta `/api/public/tienda/{slug}/opciones`; usa el día local de la tienda que devuelve la API y exige una fecha/ventana vigente sin reemplazar la elección del cliente. Forma de pago, nota y domicilio se muestran junto al resumen. Confirmar crea una clave nueva y guarda una copia inmutable de **ese** contenido antes del POST. Doble clic queda bloqueado. Si el navegador pierde la respuesta, el intento permanece con su clave, partidas, fecha, ventana, pago, nota e importe. La acción visible «Consultar o reintentar envío anterior» reenvía exactamente ese contenido; nunca envía el carrito actual bajo la clave vieja. Un intento previo se muestra en un aviso propio, incluso cuando la recepción web está cerrada. El formato anterior de `sessionStorage` se acepta si es coherente; un valor corrupto se bloquea y se pide verificar con la tienda, sin enviarlo como pedido.

La API ya guardaba clave y huella de idempotencia en la transacción del pedido. `PedidoService.CrearAsync` busca primero un pedido con la misma clave, tienda, cliente y huella, y devuelve el original **antes** de revisar horario, precio, archivo temporal o stock. Esto permite recuperar un pedido registrado aunque hoy su ventana haya vencido, sin asociar de nuevo el PDF ni descontar papel otra vez. Se conserva el contrato de `POST /api/public/tienda/{slug}/pedido`; no se agregó endpoint ni esquema. La sesión de documentos sigue verificándose en el controlador antes de entrar al servicio. Si expiró o falta, el navegador conserva el intento y pide consultar con la tienda; emitir otra sesión para el mismo teléfono no recuperaría de forma segura un documento de la sesión anterior. Tampoco se interpreta un «no encontrado» como garantía mientras pudiera existir una solicitud en curso.

El middleware de la API devuelve HTTP 400 con código de regla de negocio después de una excepción anterior al commit; solo códigos conocidos de rechazo liberan el intento. Horario, stock, producto y precio inválidos permiten editar y revisar con una clave nueva. `pdf_no_disponible` indica que hay que adjuntar el temporal otra vez; se conservan las demás partidas. Para `precio_actualizado` se consulta el catálogo vigente y se actualizan precios de partidas aún disponibles antes de una revisión nueva. Si cambió la revisión de impresión, esa partida requiere agregarse de nuevo. El frontend envía `totalEsperado` también en pedidos sin PDF; la API lo compara con el total calculado. Clientes antiguos que no envían este campo conservan su comportamiento. `idempotencia_conflicto` retiene el intento para aclaración. Respuestas de red perdidas, HTTP 5xx, códigos desconocidos y conflictos de concurrencia son inciertos: se mantiene clave y contenido. La opción de liberar un intento incierto exige una verificación explícita con la tienda; no hay «Descartar» genérico.

El service worker anterior respondía HTTP 200 con `{ "error": "Sin conexión" }` cuando fallaba una llamada `/api/`. Eso podía parecer una confirmación exitosa y borrar el intento aunque no existiera respuesta del servidor. Ahora devuelve HTTP 503, que el cliente trata como resultado incierto. El nombre de la caché se incrementó para retirar los recursos JavaScript anteriores.

El token de cliente anterior usa teléfono y no prueba posesión del número. Los límites de privacidad de sesiones de documentos descritos en [impresion-pdf.md](impresion-pdf.md) siguen vigentes. La limpieza del carrito al cerrar sesión o recargar la página es una limitación previa; este cambio conserva la captura mientras la página sigue abierta y conserva el intento de envío en `sessionStorage` para recuperarlo al recargar. Ningún dato histórico se altera.

## Validación local

- Prueba previa a la corrección, con PDF sintético: resumen con fecha nueva y POST con la antigua, HTTP 400. Después de corregir: el reintento antiguo se mostró por separado, fue rechazado con HTTP 400, se liberó su clave y el pedido revisado con fecha nueva respondió HTTP 201.
- Frontend y API reales con SQLite temporal y tienda ficticia: se simuló la pérdida de respuesta **después** de recibir la respuesta de la API para una copia física de tres caras. Dos clics inmediatos generaron un POST; el reintento envió el mismo cuerpo y clave. Quedó un pedido, el papel pasó de 95 a 92 hojas una sola vez y la nota nueva escrita después de la respuesta perdida no entró al reintento. En escritorio de 1280 px y móvil de 390 px se vio el aviso; móvil sin desbordamiento y sin errores JavaScript.
- Pruebas .NET: reintento PDF después de desactivar la ventana programada devuelve el ID anterior sin movimiento adicional; un precio cambiado en pedido sin PDF se rechaza sin guardar pedido. El conjunto pasó 100/100. Pruebas del frontend: fecha corregida, copia inmutable, formato anterior, almacenamiento corrupto, clasificación de errores y HTTP 503 del service worker sin red, 8/8. Compilación Release sin advertencias y build Vite correctos.

Se necesita publicar **API y frontend** por el cotejo de `totalEsperado` y el nuevo flujo de navegador. El nombre de caché del service worker cambió para invalidar JavaScript anterior. No hay cambio de SQLite ni paquete nuevo de la herramienta de actualización. No se usaron bases, documentos ni servicios de producción.
